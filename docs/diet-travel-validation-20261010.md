# 여행 종료 후 평소 식단 기준 복귀: 좁은 검증 보강

작성: 2026-10-10 KST / 2026-10-09 UTC. 원본 roadmap p8의 “여행 기간 감량 → 유지로 임시 변경 후 자동 복귀”에 대응한다.

## 구현 범위

기존 `DietView.tsx`는 날짜별 `ai-fitness-social-meal-mode`에 여행을 저장한다. 그 날짜에는 기존 여행 안내가 표시되고, 기간 밖에 다른 일정이 없으면 평소 식단 안내로 돌아간다. 여행 등록 때문에 전역 식단 시작일·자동/수동 단계나 과거 식단 기록을 바꾸지 않는다. 별도 여행 엔티티나 새 식단 권고를 만들지 않았다.

기존 기간 적용은 **날짜 추가/덮어쓰기**다. 범위를 줄일 때는 예정 목록에서 해당 날짜를 삭제한다. 이번 검증을 새 “여행 전체 수정” 화면이나 겹친 여행의 복원 기능 구현으로 해석하지 않는다. 다음 날에 이미 점심 외식 일정이 있다면 그 일정을 보존하며, 무조건 평소 일정으로 덮어쓰지 않는다.

## 재현한 작은 문제와 수정

기존 날짜 helper를 직접 실행했을 때 `2026-02-30`–`2026-03-03`이 `2026-03-02`, `2026-03-03`으로 정규화됐고, `2026-00-00`은 1월 1일로 정규화됐다. 이는 **잘못된 helper 입력의 합성 재현**이다. 일반적인 브라우저 date 입력이 이런 값을 허용하거나 실제 사용자가 잘못된 일정을 저장했다는 증거는 아니다.

변경은 `getDateKeysInRange` 안의 엄격한 `YYYY-MM-DD` 형식 확인과, 기존 지역 날짜 생성 후 입력 날짜와의 round-trip 대조뿐이다. 유효한 날짜의 시작/종료일 포함, 지역 날짜 키, 최대 31일 동작은 그대로 유지한다. 기존 오류 안내를 재사용한다. 스키마·API·식단 안내 변경은 없다.

## 실행한 합성 검사

`tests/diet-travel-ui.test.ts`는 실제 컴포넌트와 내부 helper를 transpile해서 실행한다. React hooks, 저장 공간, 분 타이머만 합성 경계다. 자식 컴포넌트는 실행하지 않는다.

- 같은 날, 월말, 연말, 윤년/평년 경계의 시작·종료일 포함
- 기간 중 각 날짜의 여행 안내와 종료 다음 날 평소 안내: 같은 컴포넌트의 분 타이머 갱신 및 새 인스턴스 hydration
- 전역 단계·시작일·과거 식단과 무관한 일정의 불변
- 다음 날 명시적 점심 외식 일정의 보존
- 기간 재적용, 선택 날짜 삭제, 오늘 삭제 즉시 평소 안내 복귀
- 역순·빈 값 및 잘못된 월/일/형식, 2000년/2100년 윤년 규칙
- 31일 상한과 32일째 평소 안내
- 저장 실패 시 날짜 입력 및 저장된 일정 보존, 적용/삭제 재시도

실행 결과:

- 수정 전: 12개 중 11 통과 / 잘못된 날짜 정규화 회귀 1 실패
- 수정 후 UTC: **12/12 통과**
- 수정 후 `TZ=Asia/Seoul`: **12/12 통과**
- 수정 후 `TZ=America/New_York`: **12/12 통과**. 10월 31일–11월 2일 구간은 DST 종료를 포함한다.
- 변경 컴포넌트와 두 새 시험 파일의 focused ESLint 통과
- 전체 type/lint/test/build의 최종 결과는 부모 작업의 단일 후보 검사 기록을 따른다. 작성 도중의 타입 검사에서 시험 예상값 맵의 추론 오류 3개를 확인했고 명시적 `Record<string, string>`으로 고쳤다.

원시 로컬 로그는 `yeoni-validation/diet-travel-before-guard.log`, `diet-travel-after-guard.log`, `diet-travel-seoul.log`, `diet-travel-new-york.log`, `diet-travel-discovery.log`에 구분 보존했다.

## 작성했지만 아직 실행하지 않은 인증 브라우저 acceptance

`tests/e2e/diet-travel.spec.ts`: **8개 시나리오 × Chromium/WebKit = 16개**. Discovery는 기존 auth prerequisite 4개를 포함해 20개를 발견했다. **브라우저 실행 결과가 아니다.** 기존 assertion·timeout·retry는 변경하지 않았다.

1. 320px 월 경계: 실 Auth 로그인, 기간 적용, 실제 조건부 PATCH/후속 GET 본문 확인, 각 날짜 reload, 종료 다음 날 정상 안내, 재조회 및 원본 보존
2. 390px 연 경계의 동일 흐름
3. 390px 윤년 2월 경계의 동일 흐름
4. 하루 여행 및 다음 날 기존 점심 외식 일정 보존
5. 기간 재적용, 개별 날짜 삭제, 실패한 삭제의 보존/재시도, reload 후 복귀
6. 빈/역순 날짜와 저장 공간 실패 시 서버·기기 상태 및 날짜 입력 보존, 같은 입력 재시도
7. 최대 31일과 최초 제외일 복귀
8. 다른 계정의 소유자 RLS 조회/수정 차단, 같은 브라우저 실제 로그아웃·다른 계정 로그인·원래 계정 재로그인, 계정별 일정 불변

브라우저 날짜는 앱 달력용 무인자 Date 생성만 합성하고 `Date.now`, 타이머 및 명시적 날짜 파싱은 실제 시간을 사용한다. Supabase Auth 만료 시계를 과거/미래로 옮기지 않는다. 원래 fixture의 실제 격리 Auth/PostgREST, 외부 origin 차단, 합성 계정 정리와 원본 대조를 사용한다. 로그아웃 뒤 독립 Node 검증 세션이 폐기되는 경우 기존의 소유자 재인증 helper를 사용하며, Auth/RLS 검사를 우회하지 않는다.

## 남은 acceptance

- 물리 기기·실제 여러 기기 동기화·백그라운드/자정 전환은 별도
- 운영/호스팅 자료 조회·변경, 유료 호출, 배포·commit·push는 이 slice에서 수행하지 않음
- 현재 원격 a6624c0의 CI는 이 변경보다 이전 후보다. 그 결과를 새 여행 시험의 실행 증거로 사용하지 않음

# 식단의 독립 자기응답 3종: 구현 및 검증 상태

작성: 2026-10-10 KST / 2026-10-09 UTC. 이 문서는 이번 작업 트리의 제한된 식단 변경을 설명한다. 배포·실기기·브라우저 acceptance 완료 보고가 아니다.

## 원문 및 구현 범위

원본 「AI 연이 앱 개선 로드맵」 p8, P2 「외식·회식·여행·소화 기록」은 “배고픔·폭식 충동·수면 전 과식”을 각각 명시하고, 의학적 단정 없이 반복 패턴만 표시하도록 한다. 기존 소화 응답의 복통·설사, 야식, 운동 후 식사는 이미 구현되어 있다. 이번 변경은 별개인 자기응답 세 가지를 추가한다.

- `hunger`: 오늘 배고픔을 느꼈나요?
- `bingeUrge`: 오늘 폭식 충동을 느꼈나요?
- `preSleepOvereating`: 잠들기 전에 과식했다고 느꼈나요?

모두 선택형이며 `yes`, `no`, `unrecorded`다. 기존 `ai-fitness-diet-completed-days`의 날짜별 JSON에 선택한 필드만 저장한다. 새 테이블, 컬럼, migration, RLS, 환경변수 또는 외부 AI 호출이 없다. 섭취량·야식·마지막 식사 시각으로 응답을 추정하지 않는다. 진단, 영양 목표 자동 조정, 음식의 도덕적 평가 또는 의료 권고를 추가하지 않는다.

## 데이터 및 입력 보존

- 새 필드는 실제 선택한 항목만 patch한다. 선택하지 않은 누락 필드는 누락 상태를 유지한다.
- 알 수 없는 기존 문자열·형식은 편안함/아니요/빈 값으로 바꾸지 않고 “기존 응답 형식 확인 필요”로 표시한다. 선택을 바꾸지 않으면 원래 JSON 값을 유지한다.
- 새 응답을 저장하면서 기존 `digestionStatus`, `lateSnack`, `afterWorkoutMeal`의 인식 불가 값이 정규화되어 없어지는 부작용도 좁게 방지한다. 이미 알려진 복통·설사 등 기존 선택지는 그대로다.
- 독립 검토에서 다른 탭이 바꾼 인식 가능한 기존 응답을 오래된 화면이 덮어쓰는 문제와 다른 탭이 초기화한 응답을 되살리는 문제를 회귀 검사로 재현했다. 직접 편집하지 않은 기존 세 응답은 저장 직전 최신 값을 유지하며, 최신 값이 없으면 기존 계약인 `unrecorded`를 사용한다. 사용자가 직접 바꾼 항목만 현재 선택을 적용한다.
- 저장 직전의 최신 날짜별 store를 읽고 기존 식단 저장 내용에 새 응답의 명시적 patch를 합친다. 다른 날짜와 알 수 없는 별도 필드는 유지한다.
- 세 응답을 기존 dirty/safe-reload 보호, 저장 트랜잭션, 저장 실패 시 메모리 입력 보존, 저장 후 재조회·다시 열기, 오늘 기록 초기화에 연결한다.
- 소유자별 클라우드 상태와 계정 전환 시 화면을 다시 구성하는 기존 AuthGate를 그대로 사용한다. 새로운 공유 저장소나 전역 draft를 만들지 않는다.
- 실패한 기기 저장 전의 입력은 현재 화면에서 보존한다. 아직 저장하지 않은 입력이 OS 강제 종료 이후에도 복구된다는 새 보장은 추가하지 않았다. 기기에 저장됐지만 서버 확인이 실패한 기록의 재시도·reload는 기존 동기화 경로를 사용한다.

## 요약 의미

최근 7일(오늘 포함), 두 개의 28일 기간(한국 날짜로 어제까지)에 각 응답을 별도로 표시한다.

- 분모는 해당 항목에 실제 `yes` 또는 `no`로 응답한 날짜 수다.
- `no`는 명시적 응답이며 예 비율의 0으로 계산한다. 누락/미기록/인식 불가 값은 분모에서 뺀다.
- 응답이 하나도 없으면 “미기록 · 응답 0일”로 표시하며 비율은 `null`이다. 인식 불가 응답일 수는 계산 제외 문구와 함께 별도로 표시한다.
- 28일 날짜별 근거를 제공한다. 두 기간 각각 해당 항목의 응답이 7일 이상일 때만 비율 차이를 표시한다.
- 차이가 높음/낮음이라는 관측만 표시하며 좋고 나쁨이나 원인으로 해석하지 않는다. 기존 “이 비교만으로 원인이나 건강 상태를 판단할 수 없습니다” 안내를 유지한다.

## 작성했지만 실행하지 않은 브라우저 검사

1. 320px: 세 응답의 독립 입력, 새 필드만 수정했을 때 dirty 보호, 기록 갱신 중 입력 보존, 기기 저장 실패→재시도, 저장/재조회/reload, 한 필드 편집, 기존 원본 보존, 초기화 실패→성공 및 reload.
2. 390px: 위와 같은 흐름 및 가로 넘침 검사.
3. 알 수 없는 기존 값과 없는 필드를 다른 메모 저장에서 보존, 명시적 미기록/아니요 선택, reload, 계정 전환, 다른 소유자 행 접근 배제 및 원 계정 불변.
4. 서버 확인 GET 실패 표시, 기기 저장값 유지와 reload, 재시도 후 실제 GET readback, 다시 reload.
5. 같은 브라우저의 두 탭: 새 자기응답만 편집한 탭에서 저장할 때 다른 탭의 새 응답과 소화·야식·운동 후 식사를 유지하고, 다른 탭의 초기화 뒤에는 직접 편집하지 않은 응답을 되살리지 않는지 확인.

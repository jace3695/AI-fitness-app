# 기록에 따른 전신 서킷 조정

재민님이 매주 운동표를 직접 만들 필요 없이 최근 수행능력, 허리 상태, 피로에 따라 유지·증가·교체·감소를 제안한다. 운동 홈에서 변경 전후를 확인하고 적용 버튼을 눌러야 실제 계획을 바꾼다. 수동 편집은 계속 사용할 수 있다.

## 기본 운동

- 월·수·금: 기존 전신 근력 5종목, 3라운드, 약 25~35분.
- 화·목: 낮은 강도의 전신·코어 회복형 5종목. 1라운드부터 시작하며 안내 범위는 1~2라운드, 약 10~20분이다.
- 주말: 휴식 우선, 토요일은 걷기·가동성 등을 선택할 수 있다.
- 슬라이딩보드는 현재 루틴에서만 제외하며 기존 라이브러리와 기록은 유지한다.

## 제안 기준

아래 횟수·기간은 앱의 보수적인 검토 기준이며 진단이나 개인별 치료 처방이 아니다. 날짜만으로 운동을 바꾸지 않는다.

| 판단 | 근거와 제안 |
| --- | --- |
| 유지 | 자료 부족, 최근 근력 기록 부족, 현재 구성에 적응 중이거나 이번 주 이미 조정한 경우. |
| 증가 | 마지막 적용 이후 같은 근력 루틴·계획량·기록된 저항에서 최근 3회가 여유롭고, 계획 반복수를 완료했으며, 피로가 낮고 허리 불편이 없는 경우. 한 근력 요일의 한 운동만 반복수 1회 증가. |
| 교체 | 약 2주 이상에 걸친 안정적인 근력 수행이 6회 이상 쌓이고 최근 변화 후 수행도 확인된 경우. 한 요일의 한 동작만 보완하고 본운동 5개를 유지. |
| 감소 | 최근 높은 피로, 뻐근함, 미완료·중단 또는 같은 계획·저항 조건에서 수행 저하. 다음 운동 날짜 한 번만 라운드를 줄이고 휴식을 늘림. 이미 1라운드면 휴식 제안. |
| 증상 확인 | 최근 통증·허리 악화·신경 증상 등은 증가와 교체 보류. 증상을 유발하는 운동 중단, 지속·악화 시 의료 평가 안내. 회복형 운동을 자동으로 안전하다고 판단하지 않음. |

운동 비교는 최근 28일, 증가·교체에는 최근 7일 이내의 근력 기록도 필요하다. 통증·신경 증상 검토에는 최근 14일 운동 기록과 최근 7일 컨디션을 사용한다. 미기록·미래·잘못된 날짜와 회복형 운동의 쉬운 수행을 근력 증가 근거로 사용하지 않는다.

## 교체 후보

1. 사이드워크 한 번을 지지형 햄스트링 컬(맨몸, 좌우 8회)로 교체한다.
2. 햄스트링 보완 루틴도 안정적으로 3회 이상 수행했다면 다른 근력일의 버드독을 밴드 팔로프 프레스(약한 밴드, 좌우 6회)로 교체할 수 있다.

새 동작은 전체 2라운드 이하로 도입하며 자세 안내와 지지대·밴드 고정 조건을 확인해야 적용할 수 있다. 데드버그·힙브릿지·슬라이딩보드·중량 힙힌지를 자동으로 재도입하지 않는다.

## 저장과 일관성

- `workoutAdaptiveReview.ts`가 순수 함수로 제안을 계산한다. 생성 자체는 설정을 변경하지 않는다.
- 적용 직전에 저장된 기록·설정·선택 프로그램·현지 날짜를 다시 읽고 미리보기 ID와 비교한다. 오래된 미리보기와 중복 확인을 거부한다.
- 적용한 주에는 추가 증가·교체를 제안하지 않는다. 다음 주에도 마지막 적용 이후 새 근력 기록이 필요하다. 피로와 증상은 이 제한보다 먼저 검사한다.
- 요일별 반복수는 `weeklyExerciseTargets`, 날짜 한 번의 감소는 `dateOverrides`에 저장한다. 전역 목표를 덮어써 회복일에 섞이지 않게 한다.
- 적용 요일의 이전 날짜는 기존 계획을 보존한다. 이미 작성한 기록·날짜별 예외·직접 편집한 일정은 자동 변경 대상에서 제외한다.
- 결정 이력과 계획을 같은 설정 객체에 저장한다. 저장 성공 후 화면 상태를 변경한다. 재접속 시 이력과 적용 내용을 복원한다.
- 직접 편집하는 운동량도 선택한 요일·기간에 적용하며, 좌우 운동 표기를 유지한다.
- 기존 AI 심층 분석은 참고 설명으로 제공한다. 주 5일 서킷의 실제 변경은 운동 홈의 확인 절차로 통일한다.
- 86kg은 사용자 제공 기준값으로 표시한다. 방문 날짜에 새 체중 측정 기록을 만들어 넣지 않는다. 체중 추세는 주 평균과 수행능력·피로를 함께 평가한다.

### 클라우드 브라우저 검증 중단 시점의 범위

이 절은 최초 중단 당시의 이력이다. 현재 완료·미완료 상태는 아래 "데스크톱 후속 검증과 동기화 중복 수정"을 기준으로 한다.

합성 운동 기록을 정리하는 기본 삭제 확인창에서 클라우드 브라우저의 `Input.dispatchMouseEvent`가 시간 초과됐다. 이 확인창은 화면 안에서 삭제 내용과 유지되는 기록을 보여주고 사용자가 확인 또는 취소하는 방식으로 교체했다. 교체 후 자동화 테스트 172개, ESLint, 타입 검사와 프로덕션 빌드를 다시 통과했다.

기존 브라우저 연결을 초기화한 뒤 브라우저 식별자가 새로 발급됐지만, 새 탭 생성과 탭 목록 조회가 계속 `CDP operation refresh tabs timed out`으로 응답하지 않았다. 당시 미리보기는 READY였고 조회한 error/fatal 로그는 없었다. 이 결과는 인증 후 화면·기록 저장의 정상 동작을 증명하지 않는다. 문서화된 브라우저 절차 외의 수단으로 실사용 검증을 대체하지 않았다.

브라우저 제어가 복구되면 다음 항목을 이어서 확인해야 한다.

- 수정한 달력의 허리·신경 증상 저장, 수정, 새로고침 후 재조회와 증상 보류 제안. 화면 안의 삭제 확인·취소도 함께 확인한다.
- 합성 근력 이력을 이용한 증가·교체 제안의 확인 적용, 준비 조건, 이전 날짜 보존. 현재 자동화 테스트만 통과한 상태다.
- 320px/390px 화면에서 실제 카드·확인 버튼·기록 입력 사용성, 콘솔·네트워크 오류. 수정 후 실제 화면 재확인도 남아 있다.
- 다른 기기 또는 독립 세션에서 클라우드 저장·재조회. 같은 브라우저 새로고침을 기기 간 동기화 검증으로 간주하지 않는다.
- 검증용 계정에 남은 9월 7일 합성 기록의 삭제 결과, 9월 8일 테스트 날짜 예외 및 테스트 조정 이력 정리. 실제 사용자 기록은 삭제하지 않는다.

이 항목을 완료하기 전에는 실사용 검증 전체 완료 또는 운영 반영 가능으로 표시하지 않는다. 저장소 AGENTS.md의 실사용 검증 필수 규칙에 따라 PR을 draft로 유지한다.

#### 재현과 수정

- 기존 `stableState()`는 최상위 일부 객체의 키만 정렬했다. 운동 배열 내부의 운동·세트 객체 필드 순서가 달라지면 동일한 JSON 내용도 변경으로 판정했다.
- JSONB는 객체 키 순서를 보존하지 않는다. 이 차이가 3방향 병합에서 가짜 충돌을 만들고, 기존 배열 합치기가 같은 운동을 두 번 추가할 수 있었다. 참고: https://www.postgresql.org/docs/current/datatype-json.html
- 합성 데이터 3일 × 5종목 × 3세트로 백업 복원과 서버의 객체 키 순서 변경을 재현했다. 수정 전 45세트가 90세트가 되고, 수정 전 운동의 재추가 및 삭제 운동의 복원도 발생했다.
- `cloudSync.ts`의 비교 직렬화에서 모든 깊이의 객체 키를 정렬하도록 수정했다. 원본 저장 데이터는 수정하지 않고 운동·세트 배열의 순서와 반복 개수도 그대로 둔다. 이름이 같다는 이유로 실제 기록을 삭제하거나 합치지 않는다.
- 기존에 이미 저장된 중복을 자동 삭제하는 마이그레이션은 하지 않는다. 현재 테스트 정리는 사용자 전달 결과를 유지하며, 실제 기록을 근거 없이 정리하지 않는다.
- 서로 다른 두 기기에서 같은 운동 내용을 각각 실제로 수정한 충돌 전반을 해결한 변경은 아니다. 이번 수정은 필드 순서 차이로 생기는 잘못된 변경 판단과 그로 인한 중복에 한정한다.

#### 검증 결과와 남은 실사용 절차

`cloudSync.workoutRestore.test.ts`의 신규 5개 검사는 수정 전 모두 실패했고 수정 후 모두 통과했다. 복원 후 45세트 유지, 한쪽 반복수 수정 보존, 5회 연속 병합, 서로 다른 날짜 기록 보존, 배열 순서·실제 반복 보존, 삭제 기록 미복원을 확인했다. 전체 자동화 테스트 177개, ESLint와 Next.js 프로덕션 빌드·타입 검사가 통과했다.

클라우드 브라우저는 재확인 시에도 `CDP operation refresh tabs timed out after 20000ms`로 실패했다. 합성 JSON만 조회하는 읽기 전용 Supabase 질의도 연결 도구의 `Internal error`로 결과를 받지 못했다. 이를 실제 저장·독립 세션·네트워크 검증 통과로 계산하지 않는다. DB 스키마와 실제 사용자 기록은 변경하지 않았다.

수정 미리보기에서 이어서 확인할 범위:

1. 허가된 테스트 계정에서 기존 기록을 백업하고, 재현 사례의 45세트 합성 데이터를 복원한다. 동기화 → 새로고침 → 달력 상세·통계 재조회 후 45세트와 기존 운동 개수가 유지되는지 확인한다. 백업 재복원과 동기화를 반복해도 증가하지 않아야 한다.
2. 반복수 또는 메모를 한 번 수정하고 다시 동기화한다. 수정값을 보존하고 수정 전 운동을 새 항목으로 추가하지 않아야 한다. 기존 날짜의 실제 기록은 보존해야 한다.
3. 다른 브라우저 프로필 등 저장 공간이 독립된 세션에서 같은 테스트 계정으로 로그인해 재조회한다. 양쪽의 서로 다른 날짜 기록 및 삭제·수정 결과도 확인한다. 동일 브라우저 새 탭만으로 독립 세션 통과로 표시하지 않는다.
4. 각 저장·재조회 요청의 성공 여부와 응답을 확인한다. 인증 정보나 실제 개인 기록을 보고서에 노출하지 않는다.
5. 증가·교체 적용 전후의 과거 날짜 계획과 기존 날짜 예외를 대조하고, 합성 기록·테스트 설정만 정리한 뒤 재조회한다.

기존 통과 항목을 유지하고 위 범위가 끝날 때까지 PR #188은 draft로 유지한다.

#### 요청별 네트워크 증거와 제한

Supabase Logs Explorer에서 `/rest/v1/user_app_state`의 요청 시간·메서드·응답 상태를 조회했다. 최초 복원 시점 주변에서 다음 서버 요청을 직접 확인했다(UTC).

| 시간 | 메서드 | 상태 |
| --- | --- | --- |
| 13:29:16.703 | GET | 200 |
| 13:29:16.770 | OPTIONS | 200 |
| 13:29:16.789 | PATCH | 200 |
| 13:29:16.908 | GET | 200 |

이는 경로와 시간으로 대조한 서버 로그이며 각 요청을 브라우저 요청 ID나 인증 사용자 필터로 일대일 연결한 캡처는 아니다. 응답 본문은 이 로그에 없어, 복원된 운동 배열·수정 메모·증가/교체 설정·최종 정리 결과를 별도의 읽기 전용 서버 조회와 UI로 대조했다.

추가 로그 조회는 `Backend error! Retry your query`로 반복 실패했다. Vercel 로그에서는 인증된 앱 진입 주변의 `POST /api/pin` 및 운동 코치 이력 조회 200과, 고정 미리보기 로그인 대기 시점의 `GET /api/ai/usage` 401을 관찰했다. 이 401은 운동 저장 경로 응답이 아니며 오류 원인을 단정하지 않는다. **수정·삭제·각 반복 동기화의 모든 요청 및 응답을 개별 연결하는 네트워크 검증은 부분 완료로 남긴다.**

#### 독립 세션과 남은 작업

브랜치 주소와 고정 배포 주소는 서로 다른 origin이므로 앱 저장공간을 공유하는 같은 주소의 새 탭과 구별된다. 고정 배포 탭에서 별도로 로그인이 필요한 것을 확인하고 사용자에게 같은 검증 계정의 로그인을 요청했으나, 종료 시점에도 로그인 화면이었다. 로그인 정보를 복사하거나 인증 상태를 우회하지 않았다.

따라서 **독립 세션에서의 최초 다운로드, A/B 양쪽의 서로 다른 날짜 저장, 수정·삭제 전파 및 충돌 보존은 미검증**이다. 별도 기기가 없어도 고정 배포 탭의 정상 로그인이 완료되면 독립 저장공간 간 검증을 이어갈 수 있다. 동일 origin 새 탭·새로고침·관리자 서버 조회로 이 항목을 대체하지 않는다.

남은 절차는 (1) 독립 저장공간 탭의 같은 테스트 계정 로그인 후 양방향 시나리오, (2) 로그 조회 복구 후 각 동작의 요청/응답 일대일 대조다. 재개 시 원본 기준을 다시 확보하고 합성 데이터만 복원한다. 현재 계정은 테스트 전 상태로 정리돼 있다. PR은 draft를 유지하며 실사용 검증 전체 완료나 운영 반영 가능으로 표시하지 않는다.

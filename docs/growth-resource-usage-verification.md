# 자료 활용일과 다시 살펴보기 검증

## 범위

- 자료함 `/growth/resources`에서 직접 입력한 마지막 활용일을 확인 후 저장한다. 한국 날짜 기준 오늘까지 입력하며 날짜를 비우면 미기록으로 돌아간다.
- 기록한 활용일에서 30일 이상 지난 자료를 분류·검색과 함께 모아 본다. 업로드 시각·파일 열기·루틴 완료로 활용일을 추정하지 않는다. 미기록은 실제 미사용을 뜻하지 않는다.
- 기존 파일·제목·분류·메모·루틴 연결은 보존한다. 활용일 변경은 `last_used_on`, `updated_at` 두 열에만 한정한다.
- 저장 전 행의 수정 시각과 활용일이 일치해야 변경한다. 이후 조회로 확인하며, 응답 유실 후 재확인은 GET만 실행한다. 다른 변경이나 삭제를 구분해서 안내한다. 조회 실패를 빈 자료함으로 표시하지 않는다.
- nullable 날짜 열과 제한된 UPDATE 권한만 추가한다. 기존 행의 날짜를 채우지 않으며 소유자/루틴 연결 RLS·파일 저장 권한은 유지한다. DB에서도 미래 날짜를 거부한다.
- 정식 앱 반영과 실제 iPhone 검증은 마지막 단계로 유지한다. 이번 단계에는 새 파일 업로드·열기 경로 변경이나 AI 호출이 없다.

## 검증 상태

- 로컬 단위/DB **552/552**, 동기화 **27/27**, lint·타입 통과. 새 단위/DB 10개: 한국 자정·윤년·30일 경계, 미기록/잘못된 날짜, 응답 유실, 원본 보존, 소유자 권한, 충돌, 날짜/파일 열 제약.
- 호스팅 DB에 `20260917084426_growth_resource_usage.sql` 적용 완료. 적용 전 허가된 테스트 계정의 26개 테이블 행 수·내용 해시를 확보했다. 자료함은 원래 0건이었다.
- Preview 실사용과 전체 격리 브라우저 검증을 완료했다. 브라우저 8개 신규 사례는 Chromium·작은 WebKit에서 저장/취소/미기록 복구, 충돌/다른 계정, 응답 유실, 조회 실패를 확인했다.

## 실제 Preview 검증

- 기능 커밋 `7b5453294a12fe6dd2992b271535ef80bbd880cc`, tree `98b12afe3c1c0845596e78ebe7bab640098fb700`. Preview `dpl_K9h32GLiV27GYewqxebPVNocFyac` READY.
- DB 적용 직후 26개 테이블의 기존 열 내용·건수는 모두 동일했다. 보안 Advisor는 기존 INFO 6건·WARN 1건이며 새 경고가 없다.
- 허가된 테스트 계정에 파일 객체가 없는 명시적 합성 자료 메타데이터 1건만 준비했다. 업로드 시각은 2001년, 활용일은 null로 시작했고 ‘30일 이상’ 필터에 표시되지 않았다.
- 변경 내용 확인·취소 때 서버 원본은 그대로였다. 키보드 날짜 선택으로 2026-08-18을 확인 후 저장했고, 서버에서는 활용일과 수정 시각 두 열만 바뀌었다. 화면과 새로고침 후 ‘30일 경과’ 안내 및 필터 표시를 확인했다.
- 실제 키보드로 선택한 2026-09-18(한국 날짜의 내일)은 안내와 함께 차단됐다. 날짜를 비우고 확인 후 저장하면 null로 돌아오며 수정 시각 외 모든 열이 최초 합성 자료와 같다.
- 브라우저 도구의 날짜 `fill`은 DOM 값만 바뀌고 확인 화면은 이전 값을 유지했다. 이 상태에서 저장하지 않았으며 실제 키보드 입력으로 값 일치와 저장을 검증했다. 앱 코드나 검사 기준을 이 현상만으로 바꾸지 않았다. 네이티브 Playwright 날짜 입력 결과는 CI에서 별도로 확인한다.
- 합성 자료 1건을 ID·소유자·경로·수정 시각으로 한정해 정리했다. **26개 테이블의 행 수와 내용 해시가 시작 전과 모두 일치**했다. 기존 되돌린 유산소 이력·대화도 보존했다.
- 이번 검증은 자료 메타데이터 활용일의 저장·복구 범위다. 새 파일 업로드나 실제 파일 열기는 이번 단계에서 변경하지 않았고 재검증했다고 주장하지 않는다.

## 기술 대조 결과

- 기존 Chromium 153 기록 92건, WebKit 26.6 기록 104건을 현재 `mouthAt` 계산과 대조하여 불일치 0건.
  두 구간이 겹치는 부분은 중복 집계한다. 새 브라우저 실행이 아니라 보존된 실제 렌더 표본의 재대조다.
- `/m/` 자동 구간 3.940–4.020초의 완전 닫힘과 5.200초 이후 `rest`가 유지된다.
  입을 닫는 자음 구간과 무음 구간은 다르므로 음량만으로 닫힘 오류를 판단하지 않았다.
- 고양이·인간형 각 7개 표시 시각을 오프라인 렌더하여 입 영역 밖 픽셀 채널 변화 0개.
  그림/모핑 소스 해시는 기존 브라우저 검증 당시와 같다.
- MP4 두 파일 모두 오디오·비디오 스트림 시작 0초, 비디오 30fps.
  정상 속도 오디오와 원본의 해당 PCM 구간을 대조한 최적 상관 지연은 모두 0 sample이다.
  상관계수는 A 0.999981, B 0.999813이다. AAC 재인코딩으로 파일 바이트는 원본과 다르다.
  이는 변환 과정의 정렬 검사이며 음소 정답률이나 물리 기기 지연 측정값이 아니다.
- 원본 MP3·타임라인·앱 그림/입 전환 코드의 SHA-256은 작업 전후 동일하다.
  원본 음성 SHA-256: `f598b457e49734e75a83a04e57b28f47f7a8d98ceb1aff1549942a5264b9ef2d`.
- 영상 대표 프레임의 글자·양 외형·입 전환 표시를 시각 확인했다. Codex 직접 청취로 보고하지 않는다.

구간 A의 약 4.02–4.15초에는 고주파 에너지가 이어지고, 표시 입 모양은 둥글림에서
넓힘으로 연속 전환한다. 자동 `/i/` 시작 4.090초를 사람이 듣는 정확한 경계로 확정할 수는 없다.
구간 B의 약 4.82초에서는 신호 양상이 달라지며 마지막 소리는 5.20초 부근까지 약해진다.
이 관찰만으로 각 음소의 경계를 정답 처리하거나 옮기지 않았다.
앞선 분석과 참고 공백 RMS의 소폭 차이는 이번 24kHz 디코딩과 과거 16kHz 분석 조건을 구분한다.

운영 적용 승인이나 새 TTS 승인으로 해석하지 않는다. 완료한 기기·10분 사용 검사는 반복하지 않는다.

## 재현과 증거

저장소 루트에서 실행한다. `ffmpeg`, `ffprobe`, Node.js, esbuild, `@napi-rs/canvas`,
Python의 NumPy/SciPy/Matplotlib와 DejaVu Sans가 필요하다.

```sh
node scripts/yeoni-voice/review-boundaries.mjs
python scripts/yeoni-voice/inspect-boundary-audio.py
```

- [technical-review.json](technical-review.json): 소스 해시, 과거 렌더 표본 대조, 입 영역 검사, 영상의 성격.
- [acoustic-review.json](acoustic-review.json): 음향 수치, FFprobe 정보, PCM 상관 검사, 최종 MP4 해시.
- [mouth-trace.json](mouth-trace.json): 3.300–5.376초의 1ms 간격 표시 계산. 실제 1,000fps 렌더 기록이 아님.
- [preview.jpg](preview.jpg): 구간 A의 대표 오프라인 프레임.

영상 제작 도중 AAC 패킷 복사 연결에서 약 42ms 시작 오프셋을 발견하여 PCM 중간 파일의 재인코딩 연결로 고쳤다.
`atempo=1`도 정상 속도 파형을 바꾸는 것을 확인하여 정상 구간에서는 제거했다.
최종 검사에서 두 문제 모두 해소됐다. 앱 재생 코드의 오류를 발견·수정한 기록은 아니다.

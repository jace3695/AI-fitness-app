# J6 평가 실패 뒤의 안내·중복 요청 경계 — 2026-10-28 UTC

기준: `7cd53ee5c4ec4429dee25cdfb2b2b8f6fdaab31d`, tree `c71d2f29faf83202805c80d8c35ea0f5ce017e99`. **로컬 UI/합성 회귀 개선이며 실제 Azure 평가·새 발음 품질·1회 시험 성공·운영 적용을 완료한 것이 아니다.**

## 재현과 수정

평가 요청이 실패하거나 잘못된 응답을 받으면 browser client는 그 requestId를 재사용하지 않지만 UI는 동의·내용 확인·연결 확인을 다시 허용했다. 같은 요청의 처리 여부가 불확실한데 내용 확인이 “녹음은 보내지 않았어요”로 안내를 덮거나, 이미 사용한 ID의 재시도를 사용할 수 있는 것처럼 만들었다. 새 회귀는 기존 코드에서 7 통과/1 실패였다.

- 현재 준비 자료가 시도되었는지 표시해 성공 또는 실패 뒤 같은 ID의 내용 확인·연결 확인·재전송을 비활성화하고 handler도 거절한다.
- 실패 제목을 `발음 평가 결과 확인 필요`로 표시하고 오류 안내에 `role="alert"`를 부여한다. 같은 요청을 다시 보내지 않으며 새 준비도 이전 처리 종료나 1회 한도 복구를 뜻하지 않는다고 설명한다.
- 독립 검토에서 취소/새 준비로 마지막 시도 ID가 초기화되면 오래된 handler가 다시 동작할 수 있음을 추가 재현했다. `preparedOwner`가 현재 준비 객체를 동기적으로 소유하고, 취소 시 해제·새 준비 시 교체한다. 오래된 review/check/send는 이전 객체로 현재 준비를 덮거나 요청하지 못한다.
- 기존 로컬 준비는 유지한다. 새 준비는 그 자체로 전송·readiness·동의를 만들지 않는다. 서버의 지정 계정·문장·5초·1회 시험 원장, 중복 방어, permission/보관/비용 정책을 변경하지 않았다.

## 검증 범위

- 실제 컴포넌트 handler와 기존 WAV/trial/browser-client를 연결한 회귀는 HTTP 503, 잘못된 JSON, 본문 없는 200, 네트워크 거절, 빈 metrics를 검사한다. 현재 ID 재호출, 새 준비 뒤 이전 handler, 새 ID의 두 번째 합성 시도 뒤 이전 handler, 취소 뒤 이전/현재 handler를 모두 검사한다. 두 번째 readiness는 모의 transport가 명시적으로 허용한 것이며 실제 1회 원장의 재시도 허용을 증명하지 않는다.
- focused 검사 **68/68 통과**, 변경 4파일 ESLint `--max-warnings 0`와 `git diff --check` 통과. 한 회귀 안의 다섯 fault variant를 다섯 개의 별도 테스트나 실제 서비스 성공으로 집계하지 않는다.
- 전체 `--test-concurrency=1` 단위 검사 **1,419/1,419 통과**, 실패/취소/건너뜀 0. 전체 프로젝트 `tsc --noEmit --incremental false`와 전체 ESLint도 통과했다. 최종 component bundle은 다시 빌드했다. 이 개별 후보에서 Next 프로덕션 빌드·실제 브라우저는 실행하지 않았다.
- 독립 읽기 전용 검토에서 관련 UI/client 검사 **15/15**를 재실행했고 최종 코드 차단 결함 없음으로 확인했다. focused 검사와 중복되므로 합산하지 않는다.
- 기존 격리 browser fixture에 HTTP 실패/잘못된 JSON release를 추가했다. 실패 제목·alert·잠긴 제어·키보드 접기/펼치기·로컬 새 준비·새로고침·가로 넘침 검사를 **2시나리오 × 2엔진 = 신규 4개**로 작성했다. 발견(`--list`)과 component bundle 빌드만 확인했다. 로컬 sandbox의 기존 브라우저 차단을 반복하거나 우회하지 않았으며 실제 실행은 검사용 최종 커밋의 기존 CI에서 별도 확인해야 한다.

모의 hooks/HTTP/디코더 검사는 실제 DOM/미디어·스크린리더 발화·인증된 계정·실제 공급자/원장·물리 기기 검증을 대신하지 않는다. 실제 사용자 녹음, 새 음성, 키, DB 변경, 운영 배포는 사용하지 않았다.

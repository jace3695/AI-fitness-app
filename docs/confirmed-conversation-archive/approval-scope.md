# 계정 보관본: 로컬 구현 및 DB 적용 전 범위

실제 DB 적용·설정 변경·실제 기록 조회/변경은 하지 않았다. 이 문서는 적용 승인을 대신하지 않는다. `schema-draft.sql`은 검토용 마이그레이션 초안이며 공식 CLI 생성/적용 기록이 아니다. 이전 `.supabase` 디렉터리 접근 거부 CLI를 재실행하지 않았다.

## 기존 구현과 새 구현

기존 `body_analysis_history`는 로컬 규칙 분석문 한 건의 보관이다. 이를 다시 만들거나 기존 테이블 형식을 변경하지 않았다. 새 `confirmed_conversation_archive`는 다음 두 종류의 사용자 선택 보관본을 담는다.

- `body-dialogue`: 기준일, 사용자 질문, 실제 화면의 로컬 규칙 답변 한 쌍. 사진·원본 측정 객체·다른 대화·음성은 자동으로 포함하지 않는다. 답변 문장에 수치가 있거나 질문에 개인 정보가 있으면 그 텍스트는 포함되므로 전송 전 확인·동의를 받는다. 현재 화면에서 선택한 최근 유효 질문·답변만 보관하며, 전체 대화 자동 적재가 아니다.
- `japanese-practice`: 상황, 직접 입력한 문장, 복습 표시, 자기 보고 재연습 횟수, 기존 기록에 답변이 있으면 그 텍스트. 녹음·이미지는 제외한다. 저장 당시 보관본은 불변이다. 복습 상태가 달라진 내용을 다시 선택하면 새 보관본으로 확인 저장한다. 불러온 항목은 현재 탭으로 명시적으로 가져올 수 있으며, 같은 문장 ID가 탭에 있으면 덮어쓰거나 중복 추가하지 않는다.

일본어 실제 AI 서비스는 여전히 미연결이다. 보관본의 답변 출처 표시는 사용자가 확인해 복사한 기록의 속성이며, 서버가 제공자 호출이나 AI 생성 사실을 증명하는 감사 기록이 아니다. 클라이언트의 동의 필드 또한 법적 동의 감사 로그를 대신하지 않는다.

## 정확한 대상과 변경

실제 실행 대상은 배포 서버의 Supabase 프로젝트다. 과거 메타데이터 조사에서 `Jace App Hub / piqqukiiacncfbztktga`를 확인했으나, 이번 작업에서는 실제 서비스나 기존 데이터를 조회하지 않았다. Preview가 이 프로젝트인지, Production과 공유하는지 아직 확정하지 않았다. 실제 적용 전에 프로젝트 ref·환경·공유 여부를 확인해야 한다. 비밀 키·보호 환경값은 열람하지 않았다.

신규 객체만 제안한다.

| 객체 | 제안 범위 |
| --- | --- |
| 테이블 | `public.confirmed_conversation_archive`: user_id UUID, id UUID, kind TEXT, snapshot JSONB, created_at TIMESTAMPTZ, deleted_at TIMESTAMPTZ |
| 기본키 | `(user_id,id)`; 같은 ID 재시도는 동일 내용일 때만 성공, 다른 내용은 충돌 |
| 인덱스 | 소유자·종류·저장일·ID 순서, 내용이 남은 행만 포함 |
| RLS | 소유자 SELECT, INSERT, UPDATE 정책 3개. UPDATE는 USING/WITH CHECK 모두 소유자 조건 |
| 권한 | public/anon 접근 없음. authenticated는 SELECT, 지정 열 INSERT, snapshot 열 UPDATE만 허용. DELETE/소유자·종류·시각 UPDATE는 허용하지 않음 |
| 트리거 | SECURITY INVOKER 함수 1개·트리거 1개. 원본 내용 수정과 삭제된 내용 복원을 거부하고, 기존 snapshot을 NULL로 지울 때 삭제 시각을 서버에서 기록 |
| 계정 삭제 | auth.users FK cascade. 계정 생성·삭제 자체는 이번 작업에서 실행하지 않음 |

기존 테이블, 정책, 서비스 설정, 기존 사용자 행은 변경하지 않는다. 자동 backfill과 기존 탭 기록의 자동 업로드도 없다. 실제 적용 직후에는 0행이다. [Supabase 공식 RLS 설명](https://supabase.com/docs/guides/database/postgres/row-level-security)의 소유자 조건과 명시적 최소 권한 원칙을 검토했다. changelog.md 조회는 도구의 Markdown content-type 제한으로 열리지 않았으며 새 SDK 기능이나 버전 변경은 도입하지 않았다.

## 보존·삭제·재시도

확인 저장한 내용은 사용자가 내용 삭제하거나 계정을 삭제할 때까지 보관한다. 일반 운동/일본어/비서 초기화와 별도로 유지한다는 안내를 화면과 초기화 설명에 추가했다. 원본 탭 기록을 지워도 계정 보관본은 유지되고, 보관본을 지워도 원본 탭/측정/일반 대화는 유지된다.

내용 삭제는 `snapshot=NULL`로 실제 텍스트를 제거하며 앱에서 복구할 수 없다. 늦게 도착한 동일 저장 요청이 내용을 되살리지 못하도록 요청 ID, 계정 ID, 종류, 저장·삭제 시각만 남긴다. 이 식별 정보도 계정 삭제 시 제거된다. 삭제 버튼에는 확인/취소가 있으며 자동 삭제는 없다. 실제 서비스에서 검증용 행을 정리하는 것도 계정·ID 범위와 영구 삭제에 대한 별도 승인이 필요하다.

서버는 인증 사용자와 X-Expected-Owner를 대조하고 모든 조회/내용 삭제에 소유자·종류 조건을 적용한다. 저장 응답을 잃으면 같은 화면의 같은 후보는 동일 ID로 재시도한다. 삭제된 ID의 POST는 410, 다른 내용 재사용은 409다. 정렬 시각이 같아도 ID를 함께 사용해 페이지 중복/누락을 방지한다. 클라이언트는 15초 시간 제한, 늦은 응답 무시, 계정/페이지 이탈 시 중지 및 이전 내용 제거를 적용한다.

## 적용·실제 검증·되돌리기

승인 후 필요한 최소 실서비스 검증은 별도 테스트 계정 2개, 비식별 일본어 문장 1개와 합성 질문·답변 1쌍, 지정된 비운영 프로젝트다. 저장→새로고침→조회→타 계정 접근 거부→응답 유실 재시도→명시적 내용 삭제→삭제 ID 재전송 거부를 확인한다. DB 대상/정책 적용 승인과 내용 삭제 승인은 별도다. 이 검증에는 외부 AI·유료 모델·마이크가 필요 없다.

문제가 있으면 앱 기능을 이전 후보로 되돌리고 새 테이블/내용을 보존한다. `DROP TABLE`, 트리거 해제, tombstone 제거를 자동 원복으로 실행하지 않는다. 테이블 제거는 데이터 보존·영구 삭제 승인을 따로 받아야 한다. 기존 백업은 손대지 않는다.
